Fixed by this change (38 issues -> 30):

1. missing-record B00..B05 (6 issues) - NOT a missing run. `.gitignore` keeps the protocol path
   (`<taskId>/<taskId>.handoff.json`) untracked on purpose, so a finished trail's committed records live in
   generation directories. The reader's generation list was ["", "out", "out2", "out-corrected", "out-final"]
   and did not know `out-backfill`, where the 2026-11-05 backfill put the six B-family records
   (AUDIT/integrity-scan-20261105-backfill.txt: canonical_hash_ok=113, hash offenders none). The records were
   complete, schema-conformant and hash-clean; only the reader could not see them. `GENERATION_ORDER` now ranks
   `out-backfill` BELOW every generation the run wrote itself: a reconstruction made afterwards must never
   silently outrank a record the run stamped at the time. A backfill is used only where nothing was written.

2. live-runner (2 issues, now 0) - both matched processes belonged to other projects: one was a code review of
   cartwright-spec whose prompt text contains "You MAY run `npm test`", one was a SectorDrivePrototype agent
   running `git status --short`. The old matcher attributed any process whose command line CONTAINED a recorded
   command, so an unrelated project could hold this trail's gate shut. Attribution now needs both: the process
   RUNS a recorded command (delimited by shell syntax, not quoted in prose) and it was started INSIDE the audited
   checkout. Processes that quote a recorded command from elsewhere are reported as `unattributedRunners`.

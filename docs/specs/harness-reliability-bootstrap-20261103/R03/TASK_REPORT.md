## Design the worker was held to, and delivered
A single pure `evaluateRetryBudget(input)` returning `{action:"retry", waitMs, attempt}` or `{action:"stop", reason}` with reasons `attempts_exhausted | deadline_exceeded | backoff_exceeds_deadline | bootstrap_mode | invalid_budget`, ordered bootstrap → invalid → attempts → deadline → backoff-overshoot → retry. It **imports `exponentialBackoffMs` from `src/inference/retryDelay.ts` instead of writing a second backoff formula**, and a server `retryAfterMs` dominates the computed backoff (`Math.max(exponentialBackoffMs(attempt, base, max ?? Infinity), retryAfterMs ?? 0)`), which is the behaviour `RETRY_OWNERS.md` conflict 2 shows the layers disagreeing about today. All RETRY_OWNERS ceilings (gateway 8, transient 4, stream 4, admission 50, resume 3, mission 3) arrive as `maxAttempts` **data** — nothing hard-codes or imports a layer's config, and the incident key is the existing `RetryTrace.failure_id` rather than a new identity scheme. Bootstrap mode is an **input field** (`mode?: "bootstrap" | "normal"`), because there is no bootstrap-mode flag anywhere in `src` (verified before writing the contract: no `bootstrapMode`/`BOOTSTRAP_MODE`/`bootstrap_mode` symbol), so inventing a global read would have been a hidden dependency.

## Residual gaps
- **Nothing consumes the evaluator.** Its callers (`src/guard/transient.ts`, `src/workers/PiWorkerExecutor.ts`, `src/orchestration/scheduler.ts`) are deny-listed for this unit, so RETRY_OWNERS conflicts 1, 3, 4 and 5 remain live: today four layers still decide 429 independently and zero-tool retries still bypass `max_attempts`. Adoption is the work that actually changes behaviour, and no task in the current plan names it — it needs its own unit per consumer.
- `deadlineMs` is a **duration budget** compared against `elapsedMs`, not an absolute timestamp; a consumer that holds an absolute deadline must subtract. The contract fixed that shape, and nothing in production enforces it.
- `maxBackoffMs` is optional and when absent the backoff is uncapped (`Infinity`), so a caller can produce unbounded waits while still passing the deadline check only if no `deadlineMs` was supplied. Whether uncapped-without-deadline should be `invalid_budget` is an open policy question, not a defect I resolved silently.
- The evaluator never sees `attempt` provenance: a layer that counts attempts differently (the exact disagreement RETRY_OWNERS conflict 5 documents for zero-tool retries) still gets a self-consistent but wrong answer.

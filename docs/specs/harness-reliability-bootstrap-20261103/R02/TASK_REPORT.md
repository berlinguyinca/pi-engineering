## The honest verdict on this delta: already satisfied by E07, so the unit became a contract test
The plan's delta asks for a stable cross-layer failure correlation ID plus duplicate-layer-action detection. At the base that capability **already exists**, shipped by E07 (commit `8f33cfbb`) in `src/inference/retryTrace.ts`: `failureIdentity()` (`:92`) digests `[sessionId, runId, provider, model, originLayer, firstAttempt, normalized error]` — deliberately excluding the *observing* layer and its attempt, which is exactly what makes every layer derive the same id for one upstream failure — `RetryTrace.failure_id` (`:45`) carries it, `recordRetryTrace()` (`:107`) publishes it on the `inference.retry.trace` bus, and `actingLayers()` (`:58`) over `actedOn()` (`:52`) is the duplicate-action detector (more than one acting layer = retry multiplication). I told the worker this explicitly in `R02/HANDOFF.md` and instructed it **not** to reimplement, rename or wrap that API, but to change production only if a test it wrote exposed a real gap. It wrote five tests against the API as it stands and found **no gap**, so production stayed untouched — the alternative would have been a parallel second correlation mechanism, which is the failure mode R01's catalog (conflicts 1, 3, 4, 5) documents as this subsystem's core disease. This is not `ALREADY_SATISFIED` in the handoff sense: the manifest's declared deliverable — a test file pinning the two evidence properties — was genuinely missing and now exists.

## What the tests pin (all verified by me, independently, at the commit)
1. One failure observed by two layers (`resilient-stream` and `worker-transient-retry`) yields byte-identical `failure_id` **while each layer's own attempt differs**, and the identity input's key set is asserted (`error, firstAttempt, model, originLayer, provider, runId, sessionId`) so a future field that leaks the observing attempt into identity breaks here first.
2. Independent failures stay separate: different error (429 wait vs 500), different `sessionId`, different `runId`, different `firstAttempt` — plus re-derivation of one failure being byte-identical.
3. Duplicate action reads straight out of `actingLayers`: two acting layers (`retry` + `hold`) on one correlated `failure_id` → both; one acting layer plus `defer` entries → exactly one. No new detector was invented.
4. Format compatibility: a `RetryTrace` literal with only the five original fields is valid, `recordRetryTrace(into, entry)` with no telemetry/identity still appends, and `failure_id`/`error_ref` ride the emitted payload unchanged (a real `InferenceTelemetry` subclass records name+data; no clock read).
5. Determinism and non-leakage: same input twice → same id; `errorRef` for an error whose message carries `/Users/secret/personal/token=abc` keeps only `code`, `layer`, `severity` and a 32-hex digest.

## Residual gaps
- The correlation ID is only as stable as the normalized error inside the digest: two layers that normalize the same transport failure into different `code`s (R01 conflict 3: `signals.ts:689` reads a 503 as gateway-queue pressure, `transient.ts:325` as retryable server error) will derive **different** ids for what is one failure. The tests assert separation for genuinely different inputs, so they cannot catch that; the fix belongs to the normalization layer, not to identity.
- `firstAttempt` is caller-supplied and unverified: a layer that passes its own attempt count as `firstAttempt` silently forks an identity. Nothing in production validates it; only the key-set assertion above would notice a schema change.
- Nothing consumes `actingLayers()` to *block* a second action — detection exists, enforcement does not (R01 conflict 1 remains open, and R03/R11/R13 are where ownership becomes policy).

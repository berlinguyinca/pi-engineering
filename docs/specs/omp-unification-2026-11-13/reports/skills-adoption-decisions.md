## The PE skill pack and its lock
- Path: `skill-packs/pe-operator/` (own `package.json`, `skills/pe-operator/SKILL.md`). It is an OMP extension package root. It is not under `pi.extensions`, has no `pi`/`omp` key, and nothing in PE loads it. Opt in: `omp -e skill-packs/pe-operator` or the `extensions:` setting. Operator-facing content only (/engineer, /plan, /execute, /verify, /review, /ledger and the evidence/worktree/PR rules). It ships no scripts (a unit test fails if a script-like file appears).
- `skills.lock.json`: OMP's own lock schema (`version: 1`, `skills[id] = {version, integrity, resolved}`), id `@pi_engineering/pe-operator`, integrity `sha512-yYp4e3Mq/x99EYy4RhVqPc5OiIN5QmETyfra9GYFChORLmUnCxbIikHThf6yDnyoPMMg+sjEA+KTwiLHfEqXNg==` taken from OMP's own `omp skill publish <dir> --dry-run` (deterministic across runs). `resolved` is empty: the pack is not published. The gated test recomputes it with the real OMP.
- `pack.manifest.json`: PE-side per-file sha256 + sha512 digests, checked by `verifyPack` (`src/skillpack/verify.ts`) in a CI unit test that also checks version agreement across `package.json`, SKILL.md `metadata.version` and the lock. Regenerate after an intentional edit with `node scripts/skillpack-manifest.ts`, then re-run `omp skill publish skills/pe-operator --dry-run` and update the lock integrity.
- Placing `skills.lock.json` in the pack root is inert for OMP (it reads locks only from `<project>/.omp/` and the agent dir).

## Rollback
1. Pack content: `git revert` the commit that changed `skill-packs/pe-operator/`; the CI test re-verifies digests.
2. Stop using the pack: remove `-e skill-packs/pe-operator` / the `extensions:` entry. Nothing else references it.
3. Registry-installed (third-party) packs: re-pin the previous exact version in `.omp/skills.json`, restore the previous `.omp/skills.lock.json` from git, run `omp skill update` (online) or rely on the still-present store entry (offline; test proves older locked version loads). OMP has no dedicated rollback command (confirmed from source; not found in `omp skill --help` actions).
4. Experiment code (`src/skillpack`, `src/promptcompress`, scripts, tests) is not imported by any runtime path; deleting it cannot change behavior. Production prompts were not changed.
5. Auto-learn: if ever enabled by mistake, delete `~/.omp/agent/managed-skills/*` and set `autolearn.enabled: false`.

## Decisions taken since (operator approved)
- Auto-learn overlay and foreign skill dirs: every omp process PE starts gets the firewall overlay (`autolearn.enabled: false`, memory off) plus `--no-skills --no-extensions --no-rules --no-context-files`. That covers worker runs and the negotiation handshake (`src/omp/negotiate.ts`), so a cloned repo's `.omp/config.yml`, managed skills and `.claude/.agents/.codex/.github` skill dirs do not reach them. Pinned by `test/integration/omp-firewall.test.ts` (workers, against hostile config) and `test/unit/omp-adapter.test.ts` (handshake). The operator's interactive session is PE's legacy pi session, not omp, so it has no OMP auto-learn, and its skills are left alone.
- Worker sessions may get packs: implemented as an opt-in (below).
- Store contents are not re-hashed at load: filed upstream as https://github.com/can1357/oh-my-pi/issues/19378. Pack integrity depends on the platform (the gzip OS byte): filed as https://github.com/can1357/oh-my-pi/issues/19402.

## Worker skill packs (opt-in)
Default off, byte-identical to before (legacy and `PARITY_PATH=omp` golden gates 27/27). A repository is untrusted input, so the grant is operator-only. Both switches are required:
- `PI_ENGINEERING_WORKER_SKILLS=1` (master switch), and
- the operator's `<agentDir>/engineering.yaml` (`PI_CODING_AGENT_DIR`, default `~/.pi/agent`) with `workers.skillPacks: { <role>: [{ id, manifestSha256 }] }`. `manifestSha256` is the sha256 of the pack's `pack.manifest.json`, pinned by the operator (`shasum -a 256 pack.manifest.json`). A `workers.skillPacks` in the repository's `.pi/engineering.yaml` is ignored and a `worker skill packs: ignored workers.skillPacks in the repository's ...` activity line is emitted.
- Packs resolve ONLY under `<agentDir>/skill-packs/<id>`; `id` must match `^[a-z0-9][a-z0-9-]*$` (no separators, dots or absolute paths), and nothing resolves against the worker cwd.

Gate (`src/skillpack/workerPacks.ts`, fail closed): the manifest sha256 must equal the pin (checked before anything is staged); the pack must pass `verifyPack` (per-file sha256 + sha512, lockfile agreement, no symlinks) and carry no scripts (no `scripts/`/`bin/`, no script-like extension, no executable bit, no `scripts`/`bin`/`main`/`exports`/`omp`/`pi` in `package.json`, nothing outside `skills/` except `package.json`, README.md, LICENSE, no empty directories, no files directly under `skills/`). It is copied to a content-addressed private directory (`<state dir>/worker-skill-packs/<manifest digest>`, dirs 0700, files 0600), verified as copied, and verified again immediately before each load; a bad cached copy is moved aside, never trusted. The worker loads only the copy. A refused pack means the worker runs without it and a `worker skill pack refused (<role>): <id>: <problems>` line is emitted as worker activity. No network, no script is ever run.
- Legacy path: the role resource loader returns the verified skills for that role only (`loadSkillsFromDir` on the copy).
- omp path: `-e <copied pack dir>` plus the overlay `firewall-skills.yml`: identical to the firewall overlay except `skills.enabled: true`, `customDirectories: []`, and every capability provider except `omp-plugins` is disabled (omp-managed, native, skillshare, claude, claude-plugins, agent-plugins, agents, codex, opencode, github, cursor, gemini, windsurf). `--no-skills` is dropped; `--no-extensions` stays, which makes the `-e` roots the only extension roots (upstream `injectOmpExtensionCliRoots` mode `explicit-only`). Auto-learn, memory and skill slash commands stay off. Proven against a real omp with hostile `.claude`, `~/.agents`, managed-skills and auto-learn config, and with a hostile repo shipping its own allowlist and pack: only the operator's pack appears, no `manage_skill`/`learn`.
- Context cost (pe-operator, role `scout`, first request body): omp +305 bytes (about 76 tokens), legacy +903 bytes (about 226 tokens). Ratchets in `test/integration/worker-skill-packs.test.ts` (ceilings 400 and 1100 bytes).

Residual risks and findings (security review, 2026-11-15):

- Operator-installed omp plugins (`~/.omp/plugins/node_modules/<name>` with an `omp`/`pi` manifest key and a `skills/` dir) were suspected of loading through the enabled `omp-plugins` provider. Not reproducible: installed plugins are enumerated only in extension-root `merge` mode, and `--no-extensions` makes it `explicit-only`, so only `-e` roots count. Verified against real omp: the plugin's skill leaks when `--no-extensions` is removed (control) and is absent with it (`test/integration/worker-skill-packs.test.ts`, "installed omp plugin"). No behaviour change.
- Providers are disabled by name: a provider added by a future omp is on by default under the skills overlay. The pinned omp version and the real-omp hostile-surroundings tests are the guard; bumping omp means re-running them.
- Fail closed: an unusable cache dir (symlink, foreign owner, uncreatable) or a pack dir that is a symlink is a refusal diagnostic and the worker runs without the pack; the staged copy is re-verified against the pin just before it is returned. The agent dir resolves identically on both paths (`PI_CODING_AGENT_DIR`, `PI_AGENT_DIR`, `~/.pi/agent`).
